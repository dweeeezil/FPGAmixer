FPGAmixer: how it fits together

A 20-input, 20-bus, 20-output digital matrix mixer on a Genesys ZU-3EG. A computer over USB, the network over AVB and a USB audio interface are three interchangeable "front doors" into one mixer core. The StudioRunner app controls it over OSC.

1. The network: who talks to whom

Three kinds of cable reach the board. USB-C carries the Mac's sound card, USB-A carries a MOTU M2 audio interface, and Ethernet carries the network audio, the shared clock and the control traffic.

2. Inside the board

The FPGA chip holds two halves that work as one system. The PS (processing system) is a quad-core ARM running Linux. It speaks every protocol and keeps the settings. The PL (programmable logic) is the FPGA fabric. It mixes, meters and keeps the audio clock, in hardware, on one clock. This section starts with the whole picture, then zooms in one piece at a time.

2.1 The board at a glance

audio settings and meters clock and time

Rule of thumb: anything with a protocol state machine lives in the PS, and anything with a sample-clock deadline lives in the PL. The PL part is a chain of stages sharing one 12.288 MHz clock, so a frame is always exactly 256 ticks.

The 20 I/O ports, and the patch

The core's 20 inputs and outputs are fixed to these ports. The patch (the OSC source and destination settings) decides which port each channel uses. Nothing is patched at first.

ports 0–3: USB host, MOTU M2 (link #3)
ports 4–11: USB to the Mac (link #1)
ports 12–19: AVB network audio (link #2)

2.2 Three paths through the system

Three kinds of information move through the system, each on its own path. The example follows a track played on the Mac and sent out over the network.

Audio

Example: a Mac track out to an AVB speaker

  1. The DAW plays 8 channels to the "board" sound card over USB-C.
  2. The Linux USB gadget hands the samples to the USB bridge, which writes them into link #1 by DMA.
  3. In the PL, pcm_link moves them into the core clock domain onto ports 4–11.
  4. The source patch assigns ports to channels. Input levels → input matrix → bus levels → bus matrix → output levels mix them.
  5. The destination patch puts the result on ports 12–19, then link #2 sends it to Linux.
  6. The AVB bridge wraps it into IEEE 1722 packets and sends them on Ethernet to the listener.

Every front door runs the same way, so USB in → AVB out, AVB → AVB and USB → USB all go through the same core. The Mac → board → Mac USB round trip measures about 61 ms.

Control

Example: drag a fader in StudioRunner

  1. The app finds the board by Bonjour and sends an OSC message over TCP 8000.
  2. The OSC server checks it against the parameter model: ranges, names, linked groups.
  3. A backend converts dB to a fixed-point gain and writes it into a register window over AXI4-Lite, then issues a COMMIT.
  4. The PL swaps the whole new gain bank in on the next frame strobe, so no frame ever sees a half-written update.
  5. The server saves the value to disk (crash-safe) and echoes it to every connected controller.
  6. Meters travel back: peak registers in the PL → server → UDP 8001 → the app's meters.

At boot the server replays the saved settings into the PL, so every setting survives a power cycle.

Clock

Making the network and the core agree on time

  1. The Ethernet port timestamps gPTP packets in hardware, and ptp4l keeps the board's clock (the PHC) in step with the network's.
  2. That clock's seconds tick is wired into the PL as a 1PPS signal.
  3. The PL media-clock meter counts how many core-clock cycles fit into one gPTP second.
  4. A Linux servo turns the error into a rate and writes it to the steering block.
  5. The steering nudges the MMCM's fine phase shift (up to ±88 ppm), so mclk follows gPTP time.
  6. The Mac's USB clock is steered through the UAC2 feedback endpoint. The M2 is resampled. AVB needs neither.

The network disciplines the core's own clock, so the core never has to deal with a foreign one.

2.3 How audio crosses between PS and PL: DMA

There are three identical audio links, one per front door. Each moves 8 channels in each direction between Linux and the FPGA fabric. This is one link, both directions. The PL never waits for the CPU: it pulls a frame from memory when its own clock says one is due.

  1. The app writes a period. The bridge hands 192 frames (4 ms) of 8-channel audio to the ALSA card. They land in a ring buffer in ordinary DDR memory.
  2. The formatter reads it by DMA. Its master port goes through a SmartConnect into the PS's cache-coherent port (HPC0), so it sees what the CPU just wrote with no cache flushing.
  3. Memory becomes a stream. One AXI-Stream beat per channel sample: the 24-bit sample in a 32-bit word, plus a TID that carries the channel number. It is paced by the audio clock, not by the CPU.
  4. An async FIFO crosses clocks. Pointers are Gray-coded and synchronised with two flip-flops, so the 100 MHz side and the 12.288 MHz side never see a half-updated pointer.
  5. The assembler builds a frame. It collects TID 0…7, and on each frame strobe hands the core a complete 8-channel frame. If none is ready it hands over zeros, never stale or partial samples.
  6. The core's output is captured. On the next strobe the serializer takes all 8 output channels at once. If the FIFO can't take a whole frame, the frame is dropped and counted.
  7. FIFO back to 100 MHz. The same Gray-pointer crossing, in the other direction.
  8. The formatter writes by DMA. Its S2MM engine puts the stream into the capture ring in DDR.
  9. The app reads a period. The kernel driver programmed the formatter over AXI4-Lite and gets one interrupt per period, about 250 a second, instead of 48,000.

What one frame looks like on the stream

beat 0TID 0 · samplebeat 1TID 1 · samplebeat 2TID 2 · samplebeat 3TID 3 · sample beat 4TID 4 · samplebeat 5TID 5 · samplebeat 6TID 6 · samplebeat 7TID 7 · sample

Each beat is a 32-bit word with the 24-bit sample in bits 27:4, the layout of an AES3 sub-frame, and the channel number in TID. A beat with an unexpected TID makes the assembler throw the partial frame away and wait for TID 0, so a lost beat costs one frame but never swaps channels.

Why DMA, if the audio is so small? A link moves only about 1.5 MB/s each way (8 channels × 4 bytes × 48,000), so bandwidth is not the point.

DMA decouples timing. The hardware pulls each frame on its own clock. Linux only has to keep a 16 ms ring topped up and take one interrupt per 4 ms period. The core never waits for a scheduler, and a slow CPU moment shows up as a counted underrun, never as a wrong sample. Figures are for the USB bridge's buffer geometry (4 periods × 192 frames).

Four ways the PS and PL talk

DMA: audio samples

Audio Formatter masters → SmartConnect → PS port HPC0 → DDR. Three links, 8 channels each way. Bulk streaming, no CPU work per sample.

Registers: settings and meters

The CPU does plain loads and stores into 4 KB windows at 0x8000_0000 and up, over the PS's LPD master and two cascaded SmartConnects. One window per block.

Interrupts

Each formatter raises one interrupt per direction into the PS's interrupt controller, once per period. That is how Linux knows a buffer is ready.

Wires: clocks and time

The 100 MHz fabric clock goes PS → PL. The GEM's hardware gPTP time counter (94 bits) goes PS → PL as plain signals, so the PL can timestamp its own frames.

2.4 How the PL is organised: two clocks, five crossings

The fabric runs on two clocks. The PS-facing side runs on a 100 MHz AXI clock. The whole mixer runs on one slow audio clock, so one frame is always exactly 256 ticks. Everything that has to pass between them goes through one of five named crossing patterns, each with its own scoped timing constraint.

audio settings, status, meters clock and time

The core never sees a foreign clock

Every front door bridges its own clock before audio reaches the core: Linux steers the Mac's USB clock, resamples the M2, and the AVB bridge needs neither. The only audio crossing in the PL is the pair of FIFOs per link.

Why 12.288 MHz

It is 256 × 48 kHz, so a frame is exactly 256 ticks and every block can be scheduled by counting cycles. It is made from the board's 25 MHz clock, and about 11 ppm fast until steering trims it.

Crossings are checked, not hoped for

Each pattern has its own timing constraint scoped to the module, so every new instance is covered. The build fails on negative slack or any methodology critical warning.

2.5 The mixer chain, and where DSP inserts plug in

The core is a chain of seven stages. Every stage speaks the same stream format, reads its settings from its own RAM bank and states its latency. Because every stage looks the same from outside, a new stage can be dropped between two others without rewiring them. That is the plan for EQ, dynamics and delay.

  • The levels are already the first slice of the DSP chain. The roadmap's order, input DSP → bus matrix → bus DSP → output matrix → output DSP, is the order of these stages, and each level stage sits at one of the three insert points. The exact placement of each insert is not final.
  • Today the chain is full. The seven stages use 251 of the 255 ticks a frame allows, so an EQ or compressor has no room until the core may span more than one frame (see 2.7).
  • Meters are passive. The peak-meter taps copy a stream outside the chain, so they cannot change the audio or the timing.

2.6 Time-sharing: 11 DSP slices, about 860 multiplies per frame

A DSP slice is a hardware multiply-accumulate unit. A fully parallel design gives every crosspoint its own slice, but each would work once per frame and idle for the other 255 ticks. A 20 × 20 matrix would also need 400 slices, more than the whole chip's 360. The core instead lets each slice work through a list of multiplies during every frame, at the audio clock alone and with no faster clock.

400 → 4slices for one 20 × 20 matrix, parallel vs time-shared
≈ 0.4 %use of a slice that multiplies once per frame (1 tick in 256)
≈ 250multiplies one slice can do in a frame at 12.288 MHz
144 → 1slices when the first matrix (12 × 12) went time-shared; LUTs −19 %, flip-flops −35 %

A time-shared matrix

  • Output-major lanes. Lane l computes outputs l, l+4, l+8 … For each output it sweeps all 20 inputs, one multiply-accumulate per tick. The DSP's own 48-bit accumulator holds the exact sum.
  • One read feeds every lane. All lanes sweep the same input one tick apart, so the sample buffer needs a single read port. The sample is handed from lane to lane through the DSP's A-cascade.
  • Same maths as before. Q2.16 gains and 24-bit samples, summed exactly, then shifted and saturated once. The time-shared matrix is bit-identical to the original parallel one, checked against the same reference model.
  • Uneven sizes just work. When the outputs don't divide evenly by the lanes, the spare lane slots run with gain 0 and their results are discarded.

A time-shared level stage

Because every beat leaves exactly four ticks after it arrives, a level stage never changes the order or the spacing of the stream. That fixed delay is what lets a stage be added anywhere in the chain and have its latency simply added to the total.

One frame, tick by tick

  • Latencies simply add. Each stage starts when its input beats arrive: 21 + 4 + 108 + 4 + 108 + 4 + 2 = 251 ticks, with 5 to spare before the next frame.
  • About 860 multiply-accumulates per frame (two 400-crosspoint matrices plus 60 level multiplies) on 11 slices, all clocked at only 12.288 MHz.
  • The output is one atomic update. All 20 outputs move to the links on a single clock edge at tick 251, so the links always capture a consistent frame.

The lane counts are not chosen by hand. A function evaluated when the design is built picks the fewest slices that still finish inside the frame, and refuses a size that cannot fit. Add a stage that lengthens the chain and it adds lanes by itself. Area and time are a dial you turn in one place.

2.7 Anatomy of a DSP insert

Planned, not built. The direction is decided (roadmap Phase 7 and decisions HD2 to HD7 of 2026-10-10). The details below are the proposal (LF1 to LF8, 2026-10-10) and are still open to change.

An insert is one more stage in the chain, built from a single template. Everything around it already exists: the stream format, the coefficient RAM, the register window and the meters. What the plan adds is two changes to the core's rules, and a smoother between the settings and the maths.

Two rules change

  • "Inside one frame" becomes "keeps up with the frame rate". A stage may spill into the next frame as long as it does at most 256 ticks of work per frame. Latency becomes a stated number of ticks, about 20.8 µs per extra frame.
  • Each block swaps its settings at its own frame start. The frame marker travels down the chain with the stream, so every frame sees one whole bank in every block, however late it runs.

The template every insert starts from

  • Stream in and out, a coefficient read port, a stated latency
  • A register window, RAM bank and smoother, the same pattern as today's blocks
  • A bit-exact model, random-audio testbench and stream monitor
  • A mutation harness that proves the tests can fail
  • A server-side backend that describes its OSC zone

Also planned

  • Sidechains: a second input chosen like a channel's source, read one frame late through the frame tap
  • Mute: a fade to −90 dB through the smoother, not a click
  • Retrofit: smoothing today's levels and matrices to remove clicks on fader moves
  • Spatial / binaural: its own section of the chain, not an insert
  • The library lives in its own repo, pinned here as a submodule

Why time-sharing matters here. The Phase 9 design notes estimate that 64 channels of 8-band EQ (5 multiplies per band) would take about 10 DSP slices of the chip's 360. That is a budget estimate, not a build, but it shows why the chain is built to take more stages.

3. Why an FPGA for audio hardware?

What this project actually demonstrates, with the evidence from the design. The honest version includes what the FPGA is not good at.

Latency you can state in clock cycles

The mixing core finishes every frame in exactly 251 ticks of the audio clock, about 20 µs. It is the same on frame one and frame ten billion. No scheduler, cache or interrupt sits in the audio path.

Testbenches check each block's timing to the cycle. For context, the delay you hear today is mostly Linux and USB buffering (about 61 ms USB round trip). The PL's own share is 20 µs.

Hardware reused in time, with room to spare

A parallel 20 × 20 matrix would need 400 multipliers, more than the chip's 360. Time-sharing at the audio clock does the whole chain, about 860 multiplies per frame, on 11 DSP slices, about 3 %.

Making the first matrix time-shared cut it from 144 slices to 1 and removed 19 % of the LUTs. Growing to 28 × 28 × 28 costs 23 slices, so the planned EQ, dynamics and delay library has room. Channel counts are parameters, not rewrites.

You own the clock itself

The audio clock is generated inside the FPGA and nudged in 12 ps steps (the MMCM's dynamic phase shift) by a loop that follows network time, by up to ±88 ppm. Two devices agree to 3 to 4 ns RMS over gPTP.

The PL counts its own clock cycles against the gPTP second from the PS's hardware time counter. Mixers without that access usually have to resample to match a network clock.

Bit-exact and provable

The arithmetic is fixed-point (Q2.16 gains, 24-bit saturating), so a software model gives the identical answer. 20 testbenches compare every output sample against a reference model.

A 6-hour loopback null test pushed 2.4 billion samples through USB and AVB, both directions, with zero differences.

Updates land whole

Each stage's gains sit in double-buffered RAM. A commit swaps the entire bank on one frame strobe, so no frame ever mixes old and new settings. A snapshot recall writes each bank once and commits it once, however many crosspoints change.

Meters are read-only taps on the same streams, so they cannot disturb the audio or its timing.

The hardware can change shape

On one board the design went from a 4 × 4 analog matrix, to 12 × 12 with USB, to 20 × 20 × 20 with a bus layer, levels, meters, an I/O patch and AVB. The Pmod front door was replaced by a USB interface.

Each step was new RTL and a new bitstream, with no change to the board.

In the PL: anything with a sample-clock deadline

  • Mixing: levels, matrices, patching
  • Peak metering
  • The audio clock and its steering
  • Timestamping against gPTP time
  • Atomic settings updates

In the PS: anything with a protocol state machine

  • USB device and host, UAC2
  • AVB talker/listener, AVDECC, MSRP
  • The OSC server, saved settings, snapshots
  • The gPTP daemon and the clock servo (about 1 Hz)
  • Sample-rate conversion for the M2

What it costs

  • Each hardware change is a synthesis and timing run, not a recompile
  • Clock crossings are designed and constrained by hand
  • Fixed-point maths and a fixed cycle budget per frame
  • Protocol stacks are far easier in Linux, which is why the design is a hybrid
